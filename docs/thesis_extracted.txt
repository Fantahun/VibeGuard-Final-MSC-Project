Chapter 1 
Introduction 
This chapter introduces the context, motivation, problem, objectives, method, scope, and expected 
value of the study. It frames the research within recent advances in AI -assisted software 
engineering and explains why security must be treated as a first-class concern when large language 
models are used to generate backend code for Node.js microservices. 4 5 
1.1 Background 
Large language models are changing the way software is produced. Recent research shows that AI 
systems are no longer used only for autocomplete or short code snippets, but increasingly for code 
generation, repair, summarization, and repository-level software engineering tasks [1], [2]. 6 7 A 
newer development style, often described as vibe coding, pushes this transition further by allowing 
developers to express intent in natural language while AI assistants generate or revise 
implementation details [3]. 8 
The appeal of this approach is largely driven by speed. Controlled evidence shows that AI-assisted 
programming can reduce development time in some tasks, including a study in which developers 
completed a JavaScript HTTP server task 55.8% faster when using GitHub Copilot [4]. 9 However, 
faster output does not necessarily imply secure output. The same body of literature shows that AI-
generated code may appear functionally plausible while still containing vulnerabilities, insecure 

=== Page 9 ===

2 
 
defaults, or weak implementation choices that are difficult to detect through casual review [5], [6], 
[7]. 10 11 12 
These risks become more serious in microservice-based backend systems. Although microservices 
improve modularity, scalability, and deployment flexibility, they also expand the attack surface 
through service-to-service communication, API exposure, dependency complexity, and distributed 
identity management [8], [9], [10]. 13 14 15 For a Node.js microservices environment, this means 
that insecure authentication logic, unsafe validation, dependency misuse, or poor access -control 
design can quickly propagate across multiple services and interfaces. 16 17 18 
1.2 Motivation 
The motivation for this research arises from a practical contradiction in modern software 
development. Developers are encouraged to use AI tools because they increase productivity, yet 
the same tools can generate code that is insecure, insufficie ntly validated, or poorly aligned with 
architectural constraints [4], [5], [6]. 9 10 11 
This contradiction is reinforced by recent security evaluations. Early work found that 
approximately 40% of Copilot -generated programs were vulnerable in tested scenari os [5]. 10 
More recent studies show that even strong coding agents often pass functional tests more often 
than security tests, and that current models still neglect important security properties during both 
generation and repair [7], [11]. 12 19 
The present study is motivated by the need to close this gap in a concrete engineering context. 
Rather than treating AI-generated code security as a general concern, the thesis focuses on Node.js 
microservices and proposes a framework that integrates secure promptin g, automated validation, 
and development workflow controls into the code generation loop itself. 20 21 22 
1.3 Statement of the Problem 
Despite the rapid adoption of AI -assisted coding tools, there is still no comprehensive security -
first framework that gov erns the safe use of vibe coding in production -oriented Node.js 
microservices. Existing approaches typically address only one part of the problem, such as secure 
prompting, benchmark evaluation, static analysis, or cloud -native defense mechanisms, without 
integrating them into a unified development workflow [7], [9], [10], [11]. 12 14 15 19 

=== Page 10 ===

3 
 
As a result, AI -generated backend code containing vulnerabilities such as injection flaws, weak 
authentication, insecure input handling, and access -control weaknesses ma y enter real systems 
without systematic scrutiny. This problem is intensified by what the proposal identifies as a 
verification gap, where developers increasingly trust generated code but do not examine it with 
enough depth to ensure its safety before integration. 23 24 25 
Accordingly, the problem addressed by this thesis is the absence of a security -integrated 
framework for vibe coding that can guide the generation, checking, and controlled adoption of AI-
produced Node.js microservice code in a way that im proves security without discarding the 
productivity benefits of AI assistance. 26 27 
1.4 Objectives 
The general objective of this study is to design and evaluate a Security-Integrated Development 
Framework (SIDF) for vibe coding that systematically mitigat es security risks in AI -generated 
Node.js microservices. 28 
The specific objectives are: 
1. To identify and classify common security vulnerabilities and reliability issues in AI -
generated Node.js backend code. 28 
2. To design a framework that embeds security -aware prompting, automated validation, and 
compatibility with existing DevSecOps workflows. 21 
3. To implement the framework through a prototype tool, VibeGuard, that intercepts 
prompts, invokes LLMs, and scans generated code before integration. 20 21 
4. To evaluate the framework by comparing standard vibe coding and VibeGuard -assisted 
development using metrics such as vulnerability density, development time, and test pass 
rates. 29 30 
1.5 Methods 
This research will adopt a Design Science Research  approach because t he study centers on the 
design, implementation, and validation of a new software engineering artefact. The main artefact

VibeGuard prototype as a middleware layer for AI-assisted Node.js development. 29 20 
The evaluation will use a controlled empirical study in which standard AI -assisted coding 
workflows are compared with framework-assisted workflows across representative backend tasks. 
The main evaluation measures are vulner ability density, development time, and test pass rate,

1.6 Scope and Limitations 
The study is limited to Node.js microservices  and focuses on backend tasks such as 
authentication, CRUD APIs, validation middleware, and secure file handling. It considers security 
issues relevant to this context, especially OWASP Top 10 -class vulnerabilities, input validation 
weaknesses, authentication flaws, and data-exposure risks. 30 33 34 
The proposed solution is evaluated as a research prototype rather than a production-grade industrial 
platform. Its results are also bounded by the behavior of the selected LLMs, the limitations of 
integrated static analysis tools, the available participant sa mple, and the time and resource 
constraints of the study. 32 35 36 37 
1.7 Application of Results 
The expected outcome of this thesis is a practical framework and prototype that can help software 
teams adopt AI-assisted development more safely in backend microservice projects. In practice, 
the study is expected to provide a repeatable approach for combining rapid code generation with 
security checks, thereby reducing the likelihood that vulnerable AI -generated code will be 
integrated into production systems. 38 
Academically, the study contributes to the growing body of research on AI -assisted software 
engineering by formalising the security dimension of vibe coding and by proposing an empirical 
evaluation strategy that connects code generation, validation, and software engineering workflow 
integration. 39

Chapter 2 
Literature Review 
This chapter provides the technical and theoretical background for the study. It introduces the main 
concepts underlying AI -assisted software engineering, large language model based code 
generation, secure coding, code quality evaluation, and microservice security. It also outlines the 
main engineering ideas and tools that inform the proposed framework . Unlike the related work 
chapter, the focus here is not on individual papers as isolated studies, but on the broader concepts, 
methods, and technical foundations that define the research domain. 
2.1 AI-Assisted Software Engineering 
AI-assisted software engineering refers to the use of machine learning models, especially large 
language models, to support software development tasks such as code generation, completion, 

=== Page 15 ===

8 
 
repair, summarization, translation, defect detection, and documentation [1], [2]. 1 2 In this setting, 
source code is treated as a structured language that can be modelled through token prediction, 
contextual inference, and sequence generation. This is possible because programming languages 
exhibit regular syntax, strong structural constraints, and recurring patterns that are learnable from 
large corpora of public code [1], [6]. 3 4 
The practical value of AI -assisted programming lies in its ability to reduce effort in repetitive or 
pattern-heavy tasks. Research in this area reports use cases ranging from natural-language-to-code 
generation to automated program improvement, code explanation, and repository navigation [1], 
[12], [13], [14]. 5 6 7 8 The field has therefore moved beyond simple line completion and now 
includes to ol-using agents capable of editing files, running tests, querying repositories, and 
iterating on generated code in more realistic software engineering environments [12], [13], [14]. 6 
9 10 
This evolution is important for the present thesis because the targ et problem is not limited to 
isolated code snippets. The study is concerned with backend microservice development, where 
code generation takes place within repositories, service boundaries, configuration files, and 
deployment workflows. In such settings, the quality of generated code depends not only on syntax 
or local correctness, but also on architecture, interface contracts, dependencies, security 
constraints, and operational assumptions. 
2.2 Large Language Models for Code Generation 
Large language models for code generation are typically transformer -based systems trained on 
large corpora of source code and related textual artefacts. They accept prompts in the form of 
comments, partial code, specifications, or natural language requirements, and then generate code 
token by token until a completion condition is reached [2], [16]. 2 11 
From a software engineering perspective, this capability changes the role of the developer. Instead 
of writing every implementation detail manually, the developer increasi ngly acts as a task 
specifier, reviewer, and orchestrator of generated artefacts. The literature review on vibe coding 
describes this shift as a move from assistance to more autonomous development workflows, where 
developers provide high -level intent and a ssess system outputs mainly through behaviour and 

=== Page 16 ===

9 
 
outcomes [3]. 12 The same review also notes that effective use of these systems depends on prompt 
engineering, context management, and structured interaction rather than unrestricted prompting 
alone [3]. 13 
This transition has led to the rise of agent -based coding systems. Repository -level tools such as 
SWE-agent, AutoCodeRover, and CodeAgent demonstrate that realistic software engineering 
requires more than next -token prediction. It requires file navigation , code search, structural 
understanding, test execution, debugging, and context -aware modification of existing codebases 
[12], [13], [14]. 6 9 10 14 This background is central to the present study because the proposed 
framework is designed for AI -assisted Node.js microservice development, not for standalone 
algorithmic exercises. 
2.3 Vibe Coding as a Development Context 
Vibe coding can be understood as a high -level, conversational style of software production in 
which AI systems generate substantial portion s of implementation from natural language intent 
[3]. 12 It represents a stronger form of AI assistance than autocomplete because the model is 
expected to infer design decisions, implementation structures, and sometimes even project -level 
changes from informal instructions. 
The attraction of vibe coding lies in rapid prototyping and reduced manual effort. However, the 
same abstraction that makes it productive also weakens direct human inspection of generated logic. 
As a result, developers may accept implementations that appear correct at the surface level but still 
contain architectural inconsistencies, hidden defects, or security vulnerabilities [3], [11]. 15 16 17 
This issue becomes more visible in repository-level evaluation. Recent benchmark research shows 
that many earlier secure-code benchmarks focus on single files or single functions, while practical 
vibe coding often involves multi -file editing, repeated turns, environment feedback, and large 
repository context [11]. 18 19 The distinction matters bec ause a secure function in isolation does 
not guarantee secure behaviour once dependencies, API gateways, configuration files, 
authentication flows, and data-handling paths are considered together. 
2.4 Code Quality, Correctness, and Evaluation of AI-Generated Code 

=== Page 17 ===

10 
 
Code generation quality cannot be reduced to syntactic validity alone. In software engineering, 
code quality usually spans validity, correctness, reliability, maintainability, and security [17]. 20 
Accordingly, the evaluation of AI-generated code requires broader criteria than whether a model 
can compile or produce a plausible-looking answer. 
A major challenge in this area is benchmark adequacy. Traditional evaluation benchmarks such as 
HumanEval and MBPP are useful for measuring function-level correctness, but they capture only 
one part of software engineering capability [15], [18]. 21 22 HumanEval+ extends functional 
testing by greatly increasing the number and diversity of test cases, showing that earlier pass -rate 
estimates may overstate model co rrectness when test coverage is weak [18]. 23 LiveCodeBench 
further broadens evaluation by covering self -repair, code execution, and test output prediction in 
addition to code generation, thereby better reflecting practical development activities [15]. 24 25 
Repository-level evaluation adds another layer. Real software engineering requires the ability to 
understand existing structures, modify related files consistently, and operate within large 
codebases. Benchmarks such as SWE -bench, CodeAgentBench, and ne wer repository -oriented 
security benchmarks move closer to this reality by testing whether an AI system can solve 
engineering problems inside actual repositories [13], [14], [15]. 10 22 26 
For the present thesis, this literature has two implications. First , evaluation should include more 
than raw task completion. Second, backend code generated for microservices should be assessed 
through both functionality and security-oriented measures, since a functionally correct service may 
still be unsafe in production. 
2.5 Security of AI-Generated Code 
The security of AI -generated code is now a well -established concern in the literature. The 
systematic review in this area concludes that AI-generated code is not necessarily secure and that 
recurring vulnerabilities are commonly observed across different studies, languages, and tools [6]. 
27 28 The same review notes that common weakness classes from the MITRE CWE Top 25 appear 
frequently in generated outputs and that dedicated security processes are still necessary when A I 
participates in software production [6]. 29 30 31 

=== Page 18 ===

11 
 
Empirical studies reinforce this view. Security evaluations of Copilot -generated code found 
vulnerable outputs in a substantial share of tested programs [5]. 32 Broader code -security 
evaluations show that  current models often neglect security in both generation and repair tasks, 
even when they perform strongly on functional code production [7]. 33 34 Recent literature also 
shows that security problems are not limited to general bugs. They include misuse of  security-
sensitive APIs, poor authentication logic, unsanitised input handling, hardcoded secrets, and weak 
configuration decisions [6], [7]. 35 36 
A further complication is that insecure code may still look correct to both the model user and 
downstream reviewers. The literature review highlights that human trust in AI-generated code can 
be unjustifiably high, especially when the output is readable, idiomatic, and apparently complete 
[6]. 30 This is particularly relevant in backend service development, whe re the most damaging 
vulnerabilities often hide behind normal application behaviour until triggered by malicious input 
or complex interaction paths. 
2.6 Security Hardening, Prompting, and Automated Validation 
The literature shows that AI -generated code sec urity can be improved, but current solutions are 
fragmented. One line of work focuses on model -side hardening. Controlled code generation 
methods such as SVEN attempt to steer models toward secure outputs while preserving functional 
correctness [16]. 37 An other line of work emphasises prompt quality, contextual guidance, and 
security-aware prompting, arguing that carefully structured prompts can influence whether 
vulnerabilities are introduced or avoided [6]. 38 31 
A third line of work focuses on evaluation  and validation. CodeSecEval provides a benchmark 
containing 180 samples across 44 vulnerability types to evaluate secure code generation and secure 
repair more systematically [7]. 34 The literature review on AI-generated code security also stresses 
that t esting, static analysis, fuzzing, and policy -oriented verification remain necessary because 
generated code can contain non-obvious flaws that are not reliably prevented by generation alone 
[6]. 39 
This background is directly relevant to the proposed thesis  framework. The planned system does 
not assume that prompting alone is enough, nor that post -generation scanning alone is enough. 

=== Page 19 ===

12 
 
Instead, the relevant literature suggests that secure AI -assisted development benefits from 
combining prompt discipline, autom ated validation, and explicit software process controls. That 
combination motivates the security-integrated orientation of the proposed framework. 
2.7 Microservices, Cloud-Native Security, and Access Control 
Microservice architecture decomposes a system into small, independently deployable services that 
communicate through APIs, messaging, or other lightweight mechanisms. This architecture 
improves maintainability, scaling flexibility, and modular deployment, but it also introduces 
additional security complexity [8]. 40 41 Compared with monolithic systems, microservices create 
more communication boundaries, more configuration surfaces, more dependencies, and more 
identity and trust relationships that must be secured. 
Recent review work identifies 126 distinc t vulnerabilities across 62 studies of microservice 
architectures and validates them through scans of multiple benchmark applications [8]. 40 42 43 
The same study shows that different scanning tools detect different weaknesses, which implies that 
single-tool assessment is often insufficient in complex service environments [8]. 44 
Cloud-native security literature complements this view by focusing on defensive mechanisms. 
Static-analysis-based studies show that microservice security requires attention to API protection, 
service identity, confidential data handling, least privilege, and the relationship between attacks 
and defensive controls [9]. 45 46 47 Access -control studies further identify authentication and 
authorization as central concerns in cloud -native systems and show the practical importance of 
OAuth2, JWT, mutual TLS, and architectural-level security design patterns [10]. 48 49 50 
These ideas are closely related to zero -trust thinking, even when that term is not always used 
explicitly in every study. In practical terms, the recurring design principles are explicit verification, 
strong service identity, limited privilege, protected APIs, and careful control of service-to-service 
communication [9], [10]. 46 50 For a security -integrated AI coding framew ork, these principles 
imply that generated code should be evaluated not only for syntax and functionality, but also for 
how it handles access control, identity, trust boundaries, and API exposure.

The present thesis applies these concepts in the context of Node.js backend microservices. The 
target environment consists of JavaScript -based backend services using RESTful APIs, message 
queues, and SQL databases, with security emphasis on injection flaws,  authentication problems, 
and data exposure. The intended workflow also assumes integration with GitHub, Docker, and 
standard CI/CD tooling, together with automated static analysis and testing. 51 52 
This environment is important for two reasons. First, Node.js is widely used for lightweight 
service-oriented backend development, which makes it a suitable setting for studying practical AI-
assisted coding. Second, microservices amplify the consequences o f insecure generated code 
because a weak service can become an entry point into a broader system. In such an environment, 
validation should occur as early as possible, preferably during the generation workflow rather than 
only after code has already been integrated. 53 54 55

Chapter 3. Related Work 
This chapter reviews prior studies that are closely related to the design and evaluation of a security-
integrated vibe coding framework for Node.js microservices. The reviewed works are organized 
into three themes: security assessment of AI -generated code,  security-aware generation and 
vulnerability detection, and agentic repository-level software engineering. 
3.1 Security assessment of AI-generated code 
One of the earliest and most influential studies in this area is the work by Pearce et al., which 
systematically assessed the security of GitHub Copilot’s code suggestions. The authors evaluated 
Copilot across 89 security-relevant scenarios and generated 1,689 programs, organizing the study 
around diversity of weakness, diversity of prompt, and diversity of domain.456 To identify 
insecure outputs, they combined CodeQL analysis with manual inspection and reported that 
approximately 40% of the generated programs were vulnerable.45 
The main strength of this paper is its disciplined experimental structure, which showed that 
security outcomes are sensitive not only to the target weakness but also to small prompt variations 
and domain changes.678 For example, in the SQL injection prompt -diversity experiment, the 
authors evaluated 17 prompt variants and found 152 vulnerable programs out of 407 valid outputs, 
showing that even subtle phrasing changes can shift the security profile of the generated code.79 
However, the study also has clear limitations. The authors themselves note that the scenarios were 
artificial and d id not capture the full messiness of real -world codebases and wider project 
context.10 The key lesson from this work is that AI code assistants should not be treated as 
security-neutral productivity tools; they must be paired with security-aware validation and careful 
human review.11 
A more recent evaluation framework is CodeSecEval, introduced to assess secure code generation 
and insecure code repair more rigorously. This study created a curated Python benchmark with 
180 samples across 44 vulnerability types, and importantly, the dataset includes executable secure 
and insecure code together with test cases, enabling automated Pass@k evaluation.121314 The 
authors used this benchmark to evaluate seven modern code models and showed that direct secure 
generation remains weak across many vulnerability classes. They also demonstrated that 

=== Page 26 ===

19 
 
vulnerability-aware problem descriptions can substantially improve security performance, for 
example raising Claude 3 Opus from Pass@1 13.83 to 39.89 and Pass@5 15.96 to 49.55 on  
CodeSecEval.15 
The strength of CodeSecEval lies in its executable benchmark design, which overcomes important 
limitations of earlier datasets that lacked secure reference code, complete runnable samples, or 
automated evaluation support.1617 At the same time, the study shows that gains are uneven across 
vulnerability categories, with some classes still scoring 0.0 under direct generation for GPT-4, and 
the authors explicitly note that generalizability to other programming languages remains an open 
issue.1518 The lesson for the present thesis is that  evaluation of vibe coding systems must go 
beyond functional correctness and include executable, vulnerability-specific security testing. 
3.2 Security-aware generation and vulnerability detection 
He and Vechev approached the problem from a different angle by asking whether code models can 
be actively steered toward secure or insecure generation. They formulated a new task called 
controlled code generation and proposed SVEN, a method that uses property -specific continuous 
prefixes to guide a frozen code language model without changing its weights.192021 For training, 
they curated vulnerability data from CrossVul, Big -Vul, and VUDENC, and for evaluation they 
used scenario-based security testing together with HumanEval for functional correctness.222324 
Their re sults are strong: for CodeGen -2.7B, the secure -program rate increased from 59.1% to 
92.3% under SVEN-based hardening, while functional correctness remained close to the original 
model on HumanEval.252627 
The main strength of SVEN is that it shows security can be incorporated before code is emitted, 
rather than relying only on post -generation scanning or repair.1928 This is important because it 
reframes security as a controllable generation property rather than merely a downstream detection 
problem. Still, the study remains constrained by its evaluation setup. Its core results are centered 
on scenario-based testing and mainly on the CodeGen family, and when the authors extended the 
method to SantaCoder they had to exclude several C/C++ CWEs because the model was not 
sufficiently trained for those languages.2329 The lesson here is that security -aware generation is 

=== Page 27 ===

20 
 
promising, but practical deployment requires attention to cross -model and cross -language 
generalization. 
A complementary line of work is represented by IRIS, which combines large language models 
with static analysis for vulnerability detection. IRIS first extracts candidate APIs from a Java 
project, uses an LLM to label sources and sinks for a target vulnerability class, converts these 
labels into CodeQL-style specifications, runs taint analysis, and then uses an LLM again to filter 
false positives.3031 The system was evaluated on CWE -Bench-Java, a dataset of 120 
vulnerabilities across large compilable Java projects averaging about 300,000 lines of code each.32 
With GPT-4, IRIS detected 55 vulnerabilities, which is 28 more than CodeQL, achieved a lower 
average false discovery rate than CodeQL, and identified four previously unknown vulnerabilities 
in later project versions.333435 
The major strength of IR IS is that it shows how symbolic analysis and LLM reasoning can 
complement each other. CodeQL supplies precise path-based analysis, while the LLM helps infer 
project-specific security knowledge that static analyzers often miss.3631 However, the paper also 
reports important limitations: IRIS still misses many vulnerabilities, it incurs additional analysis 
cost because it makes many LLM calls, its generalization beyond Java is unknown, and the 
resulting reports still do not fully match what developers need in  practice.37 The lesson for this 
thesis is that secure vibe coding frameworks should not rely on a single validation technique. 
Instead, they should combine static analysis, contextual reasoning, and developer-usable feedback. 
3.3 Agentic repository-level software engineering 
Beyond single-function generation, recent work has started to address repository-level coding with 
tools and agents. CodeAgent is one of the clearest examples. The paper presents a tool -integrated 
agent framework for repo -level code ge neration, where an LLM can use external tools for 
information retrieval, code implementation, and testing, supported by strategies such as ReAct, 
OpenAIFunc, rule-based control, and tool planning.383940 To evaluate the approach, the authors 
constructed CodeAgentBench, a repository-level benchmark with 101 functions and classes from 
real GitHub projects, selected across five common software topics.4142 Their experiments on nine 
LLMs showed repo-level pass-rate improvements ranging from 2.0 to 15.8 points, with the GPT-

=== Page 28 ===

21 
 
4 setting achieving a 72.7% relative improvement over the non -agent baseline.4344 They also 
reported gains on HumanEval, where Pass@1 improvements ranged from 6.1 to 9.7 across selected 
models.45 
The main strength of CodeAgent is that it treats coding as a tool-mediated repository task rather 
than a pure next-token prediction problem.4640 This makes the method much closer to practical 
software development, where navigation, dependency inspection, and testing are essential. 
However, the study is explicitly an early exploration. The authors acknowledge that contamination 
risk in the benchmark is not yet fully ruled out, that only simple tools were incorporated, and that 
comparisons with commercial IDE products were manual rather than rigorously stan dardized.47 
The lesson for this thesis is that agentic support is useful for handling complex repositories, but 
security assurance must be added as a first-class concern rather than assumed to follow from better 
task completion. 
AutoCodeRover moves even closer to practical maintenance by focusing on autonomous program 
improvement for real GitHub issues. The method combines LLM reasoning with abstract syntax 
tree based code search, iterative retrieval, and optional test -based fault localization, while using 
only the natural-language issue description and the repository checkout as required inputs.484950 
On SWE -bench lite, AutoCodeRover resolved 19% of issues at pass@1 and 26% at pass@3, 
averaging 195 seconds and about $0.43 at pass@1, and it compared favorabl y with Swe-agent in 
both effectiveness and cost efficiency on that benchmark.515253 
A major strength of AutoCodeRover is its software -engineering orientation. Instead of treating a 
repository as a flat bag of files, it exploits program structure and fine -grained retrieval, which 
helped it uniquely solve cases where AST-level context mattered.5455 Its weaknesses are equally 
informative. The authors show that many failures came from unimplemented search APIs and, 
more fundamentally, from the difficulty of inferring developer intent or specifications from issue 
descriptions alone.555657 The lesson is that autonomous coding agents benefit greatly from 
structured retrieval and validation loops, but they still require stronger specification support and 
cannot be assumed to produce secure outputs automatically.5750

4.2 Design Goals and Solution Requirements 
The design of the proposed solution is motivated by a central concern established in the 
proposal: AI-assisted vibe coding increases development speed, but this speed is not matched by 
an equivalent increase in developers’ ability to verify correctness and security in generated 
code.10 This imbalance creates what the proposal calls a verification paradox, where 
developers gain productivity through generation yet lose assurance because they often accept AI 
output without sufficiently rigorous review, especially in security-sensitive software 
contexts.1011 
This problem is particularly significant for Node.js backend microservices. The proposal 
identifies this domain as practically important and under-served by existing secure AI-assisted 

=== Page 32 ===

25 
 
development frameworks, despite the fact that it commonly involves security-critical features 
such as authentication, CRUD APIs, validation middleware, secure file handling, message 
queues, and SQL-backed services.121314 It further notes that current LLM-generated code 
frequently reproduces insecure patterns such as unparameterized queries, hardcoded secrets, 
weak authentication logic, unsanitized input handling, and insecure serialization paths.15 
The proposed framework is therefore designed around six main goals. First, it must support 
security by design, so that security is introduced at the point of code generation rather than only 
after the code has already entered the development workflow.516 Second, it must provide 
generation-time validation, so that AI-generated code is evaluated immediately after generation 
and before repository integration.417 Third, it must remain compatible with practical 
development workflows, particularly Git-based version control, Dockerized services, and 
standard CI/CD pipelines.188 
Fourth, the framework must be microservice-aware, since the solution is not intended for 
generic programming tasks alone but specifically for Node.js microservice systems with 
distributed interfaces and service boundaries.1419 Fifth, it must preserve human-centered 
governance, meaning that the framework assists and constrains developers but does not remove 
their final responsibility for accepting or rejecting code.20 Sixth, it must support auditability 
and traceability through systematic provenance logging of prompts, generated outputs, 
validation findings, and decisions, since current AI-assisted workflows lack standardized trust 
and audit mechanisms.2111 
From these goals, the main solution requirements can be stated as follows. The framework must 
intercept developer prompts before they reach the LLM, classify the request according to its risk 
profile, enrich security-sensitive prompts with appropriate constraints, orchestrate code 
generation, validate outputs using static analysis, apply policy-driven acceptance or rejection 
logic, log the full generation trace, and remain usable within ordinary Node.js microservice 
development workflows.2251823 
4.3 Overview of the Proposed Solution 
The proposed solution of this thesis is the Security-Integrated Development Framework 
(SIDF), a framework for governing AI-assisted code generation in a way that embeds security 
controls directly into vibe coding workflows.47 SIDF is instantiated through a prototype called 
VibeGuard, which is designed as a Node.js-based middleware and command-line tool that sits 
between developer prompts, large language model APIs, and security analysis tools.225 
Conceptually, SIDF treats vibe coding as a controlled software engineering process rather than as 
unconstrained conversational prompting. In a conventional workflow, a developer submits a 
natural-language request directly to an LLM, receives generated code, and then decides 
informally whether the output is acceptable. In the proposed framework, this direct path is 
replaced by a mediated pipeline in which prompts are intercepted, risk-assessed, enriched where 
necessary, submitted to the model under explicit security constraints, and then validated before 
they can be accepted as usable output.422524

The framework is designed to support common Node.js microservice development tasks such as 
implementing authentication flows, CRUD services, validation middleware, secure API 
integration, and secure file handling.1314 In each case, SIDF introduces a control loop that 
attempts to reduce the probability that insecure patterns pass from a prompt into generated code 
and then into the repository or deployment pipeline. The framework therefore combines 
preventive controls, detective controls, and governance mechanisms into a single structured 
workflow.52125 
From a design science perspective, SIDF is the conceptual research artifact, while VibeGuard is 
the executable prototype used to instantiate and evaluate that artifact in practice.49 This 
distinction is important because the research contribution is not limited to building a tool. The 
thesis also contributes a formal framework that defines how secure vibe coding should be 
structured, governed, and evaluated in a production-relevant software engineering setting.926 
4.4 Architecture of the Security-Integrated Development Framework 
The overall architecture of SIDF is organized into six cooperating layers: the developer 
interaction layer, the prompt intelligence layer, the LLM orchestration layer, the validation 
and policy layer, the provenance and feedback layer, and the delivery and integration layer. 
This layered organization is appropriate because the university guideline expects the proposed 
solution chapter to define the components of the system, their interactions, and the flow of 
information among them.1227 
At the highest level, the architecture begins with developer intent and ends with a gated decision 
on whether generated code should be accepted, revised, or rejected. Between these endpoints, the 
framework creates a controlled path through which code generation is transformed from a raw 
conversational act into a secure engineering process. This architectural decision directly 
addresses the lack of structured methodology for integrating vibe coding into rigorous 
development lifecycles, a gap explicitly identified in the proposal.1121 
4.4.1 Developer Interaction Layer 
The developer interaction layer is the entry point of the framework. Its purpose is to capture a 
development task expressed in natural language and ensure that the request is routed through the 
framework rather than sent directly to an LLM. In the proposed prototype, this layer is 
implemented through the VibeGuard command-line interface and middleware wrapper described 
in the proposal.225 
This layer is intentionally minimal. It does not attempt to replace the developer’s integrated 
development environment or general-purpose coding assistant. Instead, it establishes a controlled 
access point for AI-assisted generation, ensuring that each coding request enters the same 
governed pipeline. This decision is especially important in vibe coding contexts because 
developers often interact with AI systems in an informal and rapid manner, which increases the 
risk of bypassing structured verification.1028 
4.4.2 Prompt Intelligence Layer 

=== Page 34 ===

27 
 
The prompt intelligence layer performs the first core reasoning task of the framework. It inspects 
the developer’s request, identifies whether the task is security-sensitive, and determines whether 
prompt enrichment is required. The proposal explicitly states that the framework will provide 
automated enrichment of prompts and security-aware prompt engineering support.1829 
The logic of this layer follows a straightforward principle. Not all prompts require the same level 
of control. A request to generate a simple data formatter is not equivalent to a request to 
implement login middleware, file upload handling, token generation, or a database-backed API 
endpoint. The framework therefore classifies prompts according to risk categories derived from 
the architectural and security context of the requested task. Prompts involving authentication, 
authorization, SQL queries, secrets, user input, file operations, inter-service communication, or 
external API access are treated as security-sensitive and are enriched with security constraints 
before model invocation.151830 
The proposal’s technology and security scope provides the basis for these enrichments. The 
framework focuses on OWASP Top 10 vulnerabilities, with emphasis on Node.js-specific risks 
such as injection, authentication flaws, and data exposure.18 Accordingly, the prompt 
intelligence layer may inject guidance such as parameterized database access, secure secret 
handling, input validation, secure file path management, token-based authentication 
expectations, least privilege assumptions, or API gateway awareness when such concerns are 
relevant to the task.313233 
4.4.3 LLM Orchestration Layer 
The LLM orchestration layer manages communication with the underlying language model. It 
receives the enriched prompt, forwards it to the selected model provider, captures the response, 
and normalizes the generated output into a form suitable for downstream validation and 
logging.2221 The proposal indicates that the research is intended to work with contemporary 
frontier models while remaining extensible across different model versions and providers.14 
This layer is designed to isolate the rest of the framework from the volatility of LLM 
ecosystems. The proposal correctly notes that model behavior changes over time as new 
versions, parameter updates, and training adjustments are released, meaning that findings 
obtained on one model version cannot automatically be generalized to future versions.3435 By 
isolating model access behind a stable orchestration layer, SIDF can preserve a consistent 
security workflow even when the underlying generation engine changes. 
A second responsibility of this layer is metadata capture. For each generation event, the system 
should record the model identifier, timestamp, enriched prompt, output artifact, and any 
generation settings relevant for later auditing or empirical analysis. This is necessary because one 
of the explicit objectives of the proposal is to enable structured comparison between baseline 
vibe coding and VibeGuard-assisted workflows using measurable outcomes such as vulnerability 
density, development time, and test pass rate.2321 
4.4.4 Validation and Policy Layer

The validation and policy layer is the security core of the framework. After code is generated, it 
is passed through an automated validation stage before it is accepted as an approved output. This 
stage implements the proposal’s objective of embedding automated validation into the vibe 
coding workflow using static analysis tools and security-aware checks.51836 
This layer contains four logical elements. The first is the static analysis engine, which runs 
SAST tools on the generated Node.js code. The proposal specifically identifies open-source tools 
such as ESLint with security plugins and Semgrep as part of the intended solution scope.36 The 
second is the rule and policy engine, which checks whether the output violates framework-level 
constraints, such as mandatory authentication patterns, restricted secret handling, or unsafe API 
behavior. The third is the risk classification unit, which maps findings to severity categories. 
The fourth is the decision gate, which determines whether the code should be accepted, sent 
back for regeneration, or escalated to the developer for review. 
The choice to place automated validation immediately after generation is strongly supported by 
the research base. Recent work on secure evaluation of LLM-generated code identifies static 
analysis as a preferred mechanism for early-stage detection of vulnerabilities in generated source 
code.3738 Secure vibe coding literature also argues that the prompt-generate-validate cycle must 
include real-time or near-real-time feedback so that insecure output can be flagged or corrected 
before it becomes part of the normal development flow.2417 
The decision gate is the element that converts analysis into action. This is a major difference 
between SIDF and a simple security scanner wrapper. A conventional scanner may only report 
findings and leave interpretation entirely to the developer. By contrast, SIDF interprets findings 
operationally. Critical injection paths, hardcoded secrets, authentication weaknesses, or unsafe 
file system patterns may result in automatic rejection and regeneration. Moderate-severity issues 
may lead to warnings and explicit developer confirmation. Clean or policy-compliant outputs can 
be approved and passed forward. In this way, the framework embeds security enforcement into 
the act of generation itself.51539 
4.4.5 Provenance and Feedback Layer 
The provenance and feedback layer provides the persistent memory of the framework. The 
proposal emphasizes that current AI-assisted workflows lack systematic provenance logging and 
that developers often lack trust metrics for AI-generated code.1121 The proposed solution 
addresses this by recording the full trace of each coding session, including the original prompt, 
enriched prompt, model information, generated output, validation findings, decision outcome, 
and any subsequent regeneration events.2123 
This layer serves several important purposes. First, it supports auditability, which is essential 
when AI-generated code is used in security-sensitive applications. Second, it supports empirical 
evaluation, since the thesis aims to compare vulnerability density, development time, and test 
outcomes between standard vibe coding and framework-assisted development.2313 Third, it 
supports organizational learning, because stored traces can later be analyzed to identify 
recurring insecure prompt patterns, recurring vulnerability classes, and areas where additional 
policy rules or prompt templates are needed.

framework should return not only an error state but also a structured explanation to the developer 
or to the regeneration step. This aligns with the broader secure vibe coding principle that 
automated tooling should empower the developer with immediate and actionable intelligence 
rather than produce delayed and opaque security reports.20 
4.4.6 Delivery and Integration Layer 
The delivery and integration layer connects the framework to the broader software engineering 
environment. The proposal explicitly states that the framework should be compatible with 
GitHub, Docker, and standard CI/CD tools, and that later iterations of the prototype will include 
pluggable validation engines, containerization, and support for multiple analysis tools.1840 
This layer matters because Node.js microservice security does not end at source code generation. 
Microservice systems expose multiple APIs, involve service-to-service communication, and are 
deployed through containers and pipelines. Research on cloud-native and microservice security 
consistently identifies the need for security policy enforcement points, API gateways, least 
privilege, token-based authentication, and container scanning as core parts of a secure 
architecture.41323342 
SIDF therefore does not operate as an isolated code-generation utility. Instead, it is positioned as 
an upstream control layer within a secure software delivery pipeline. Its role is to reduce the 
number of insecure artifacts that reach repository integration, build packaging, or deployment. In 
practice, this means that only outputs that pass framework validation should move forward to 
normal repository, testing, and CI/CD stages. 
4.5 Core Components of VibeGuard 
The prototype implementation of the framework is represented by VibeGuard. While SIDF 
defines the conceptual model, VibeGuard operationalizes that model through a set of concrete 
components that collectively implement secure vibe coding for Node.js microservices.422 
4.5.1 Prompt Interceptor 
The prompt interceptor is responsible for receiving the developer’s raw natural-language request 
and ensuring that it cannot bypass the framework’s control path. This component establishes the 
boundary between uncontrolled prompting and governed AI-assisted generation. Without this 
intercept point, it would be impossible to guarantee that prompts are assessed, enriched, or 
logged consistently.22 
4.5.2 Security-Aware Prompt Enricher 
The security-aware prompt enricher transforms a raw request into a constrained request when the 
task is identified as security-sensitive. For example, if a developer asks for an authentication 
middleware or a file upload endpoint, the enricher can insert additional instructions requiring 
secure secret management, path validation, access checks, and safe defaults. This component is 
central to the proposal’s claim that the framework will support security-aware prompt 
engineering rather than rely solely on post-generation review.52930

4.5.3 Generation Manager 
The generation manager submits the enriched prompt to the chosen model and collects the 
generated artifact. It also manages retries and regeneration when the validation layer rejects a 
result. This component is especially important because the framework is not based on a single-
pass generation assumption. Instead, it assumes that secure output may require iterative 
refinement, particularly when the first generation contains policy violations or high-severity 
vulnerabilities.2217 
4.5.4 Validation Orchestrator 
The validation orchestrator coordinates the execution of the configured analysis tools. In the 
proposed research scope, these tools include ESLint-based security checking and Semgrep-based 
rule matching, though the architecture is explicitly designed to support pluggable validation 
mechanisms in later iterations.3640 The orchestrator standardizes tool outputs so that the 
downstream policy engine can reason over them consistently. 
4.5.5 Policy and Decision Engine 
The policy and decision engine interprets the findings returned by the validation orchestrator and 
maps them to one of the allowed outcomes: accept, reject and regenerate, or warn and escalate 
for human review. This component embodies the framework’s governance logic. It is what turns 
VibeGuard from a passive analyzer into an active development control mechanism. In the 
context of this thesis, this component is crucial because the research problem is not only the 
existence of insecure code, but the absence of a structured methodology for deciding how AI 
outputs should be treated before integration.1143 
4.5.6 Provenance Logger 
The provenance logger stores all events and artifacts required for auditability, repeatability, and 
evaluation. The proposal explicitly argues that current workflows lack trust metrics and 
provenance tracking for AI-generated code and that such omissions make it difficult to scale 
secure adoption of vibe coding.1121 By contrast, VibeGuard retains the coding session as a 
structured trace, thereby enabling later inspection of how a particular output was generated, what 
rules were applied, and why a final decision was made. 
4.6 Operational Workflow of the Framework 
The operational logic of SIDF can be understood as a gated prompt-to-code control loop. This 
loop consists of six stages: intent capture, prompt classification, prompt enrichment, controlled 
generation, automated validation, and policy-driven decision and logging.52221 
In the first stage, the developer submits a natural-language intent describing the desired 
functionality. This may include implementing an API endpoint, generating middleware, adding 
authentication to a service, or creating a secure integration with a database or external 
service.1314 In the second stage, the prompt intelligence layer classifies the task according to its 
security relevance. If the request falls into a security-sensitive category, such as authentication, 
SQL access, secrets, or file operations, the prompt is tagged for enrichment.1830

4.7 Security Integration in Node.js Microservices 
A major strength of the proposed solution is that it is designed specifically for Node.js 
microservices, rather than for AI-generated code in the abstract. The proposal explicitly limits 
the technology scope to JavaScript backend services based on RESTful APIs, SQL databases, 
and message queues, with a security focus on OWASP Top 10 classes and Node.js-relevant risks 
such as injection, broken authentication, and data exposure.1418 
This specialization is justified because microservices introduce architectural properties that affect 
both generation and validation. They expose many service endpoints, increase the attack surface, 
and distribute security-relevant logic across authentication services, business services, gateways, 
middleware, and storage layers. Security research on microservice architectures repeatedly 
emphasizes that API gateways act as security policy enforcement points and that secure designs 
must incorporate authentication, authorization, least privilege, and defense in depth across 
service boundaries.41443133 
The framework supports Node.js microservice security at three levels. At the generation level, it 
constrains prompts and outputs so that code generation is less likely to introduce insecure 
defaults, unsafe query handling, exposed credentials, or weak token logic.155 At the service 
construction level, it validates the generated code in the context of common microservice 
concerns such as input validation, access control boundaries, middleware sequencing, and 
service API behavior.3925 At the delivery level, it aligns with cloud-native best practices such 
as API gateway enforcement, token-based identity, least privilege, and container scanning, 
thereby making the proposed framework consistent with secure microservice deployment 
practices rather than limited to local source code generation alone.324233 
This layered treatment of security is important because the proposal explicitly states that existing 
approaches rarely account for architecture-specific constraints such as microservice patterns,

addresses this gap by designing the solution around those constraints from the beginning, instead

4.8 How the Proposed Solution Addresses the Research Problem 
The problem addressed by this thesis is not merely that AI systems can generate insecure code. 
That observation is already well established in the literature and in the proposal. The deeper 
problem is that there is no comprehensive, security-first workflow for controlling how AI-
generated code is produced, assessed, and admitted into development processes for Node.js 
microservices.464312 
SIDF addresses this problem in several direct ways. First, it reduces blind trust in AI output by 
intercepting generation before code reaches the developer or repository in uncontrolled 
form.1022 Second, it shifts validation from a late-stage or optional activity into a mandatory part 
of the generation workflow through prompt enrichment and automated analysis.51817 Third, it 
introduces architecture-aware controls suitable for the realities of Node.js microservice 
development, including API-centric design, authentication boundaries, and distributed service 
interfaces.1419 
Fourth, it generates measurable evidence of trustworthiness by logging prompts, outputs, 
findings, and decisions in a structured way that supports comparative analysis between standard 
vibe coding and framework-assisted coding.2321 Fifth, it supports practical adoption by being 
designed for integration with the ordinary toolchain of modern software development, including 
Git workflows, Dockerized services, and CI/CD processes, instead of requiring a separate 
academic testbed disconnected from practice.188 
For these reasons, the proposed solution does not only mitigate individual vulnerabilities. It also 
addresses the structural weakness in current AI-assisted development practice, namely the 
absence of a repeatable, policy-governed method for secure AI code generation in production-
relevant software engineering environments.1121
